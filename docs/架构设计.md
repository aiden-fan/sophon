# 架构设计

[← 文档索引](文档索引.md) · [仓库首页](../README.md)

---

> **设计要点速查（与会话/模型相关的近期约定）**  
> 1. **面向用户 vs Agent 能力（相互独立）**：**凡面向连接/请求/用户可见策略**（HTTP、gRPC、安全、**Request Gate**、会话持久化 I/O、SSE）均在 **Spring 托管**；**凡 Agent 推理与能力**（`AgentFactory`、`AgentEngine`、Registry、Tool/MCP、LLM、`Unified*`）均在 **`core.*`**，**不依赖 Spring**。**Request Gate 仅为 Spring Bean，不进 `core`**（见 **「背压与请求门控」**）。  
> 2. **Spring 与 Agent 拆分**：**会话记录、会话级配置、消息落库** 由 **Spring 持久化服务**；**一次用户对话** = **Gate 准入后** **加载会话 → `core` 组装并执行 → Spring 写回**。详见 **「分层」**、**「用户对话路径」**。  
> 3. **会话级 Agent 绑定**（增删 Tool、知识库等）：REST + DTO + **落库** 在 Spring；**绑定语义与再组装** 在 **`core.SessionAgentBindingService` + `AgentFactory`** → **「会话级 Agent 绑定配置」**。  
> 4. **全链路 `Unified*`**；**仅 `LLMClient`** 做厂商 format；**DB 中消息 JSON** 仍为统一模型 → **「LLM 客户端抽象与统一消息模型」**。  
> 5. **流式落库**、**`AgentInstance` 缓存**：见 **「流式响应与持久化策略」**、**「Agent 实例缓存与再组装策略」**。  
> 6. REST 示例：**[HTTP接口参考.md](HTTP接口参考.md)**；根目录 **[llms.txt](../llms.txt)**。

### 分层：Spring 与领域核心

**目标**：把 **「由 Spring 容器托管的边界」** 与 **「实际 Agent 运行时（领域核心）」** 划清，避免「持久化算谁的、组装在哪一步」含糊。

#### Spring 容器托管（`server` 进程内、Spring 管理的 Bean）

- **传输与安全**：HTTP/gRPC **接入**、路由、认证与鉴权过滤器、DTO 绑定与校验、SSE/WebSocket 适配。
- **Request Gate（背压/准入）**：**必须** 实现为 **`api.gate` 下的 Spring Bean**（如 `RequestGate`），**队列、并发上限、限流、超时拒绝** 等均在 **Spring / Web 层** 完成；**`core.*` 不包含** Gate 实现、**不依赖** WebFlux/Reactor 的准入逻辑。请求 **仅在经过 Gate 准入之后** 才进入「加载会话 → `core`」路径。
- **会话与配置的持久化 I/O**：**会话元数据**（`session_id`、创建时间、当前 `llm` 等）、**会话级配置**（含 Agent 绑定：Tool 列表、知识库 id 等）、**消息历史**（`Unified*` 规范 JSON）的 **读取、写入、事务提交、迁移由 Flyway/Liquibase 触发的数据源** —— 均作为 **Spring 托管的 Repository / `SessionPersistenceService`（命名可调整）** 实现；**Controller 不直接堆 SQL**，经上述服务或 **应用层用例类**（如 `ConversationApplicationService`）调用。
- **用例编排（薄编排，非领域逻辑）**：在单次请求线程（或 Reactor 链路）内顺序一般为：**按 `session_id` 从存储加载会话聚合数据** → **调用 `core` 门面传入「已加载快照」** → **取得本轮输出与待持久化增量** → **在同一事务或明确一致性边界内写回存储**。此处 **不写**「如何根据 Tool 列表解析 Registry」等规则，只做 **I/O 与调用顺序**。
- **REST 等 API**：**会话级 Agent 绑定** 的 HTTP 契约、错误码映射在 **Controller**；改绑定后 **先** 调 **`core` 计算新绑定快照与合法性**，**再** 由 Spring 侧持久化服务 **save**。

#### 领域核心 `core.*`（Agent 实际运行时，与 Spring 解耦）

- **不负责** 直接持有 `DataSource` 或声明式事务；**接收** 由 Spring 传入的 **已反序列化** 的会话快照（领域对象或 DTO，与 `Unified*` / `SessionConfig` 对齐）。
- **负责**：**`AgentFactory` / `AgentAssembler`** 根据 **当前会话配置 + 绑定 + Registry** **组装 `AgentInstance`**；**`AgentEngine`**、Orchestrator、Tool/MCP 调度、**`LLMClient`**、**`Unified*`** 消息管线、**`SessionAgentBindingService`**（绑定变更的**领域规则**）、**`SessionManager`** 中与 **推理过程、独占连接、内存态上下文** 相关的部分。
- **输出**：向调用方返回 **本轮推理结果**（流式事件或完整响应）及 **「待持久化」结构**（新增消息、更新后的配置/绑定快照等），由 **Spring 侧** 落库。

#### 用户对话路径（加载 → 组装 → 执行 → 持久化）

```
Client 请求（含 session_id）
    → Spring：鉴权、Request Gate（若启用）
    → Spring：SessionPersistenceService.load(session_id)
         得到：元数据 + SessionConfig + 消息列表（Unified JSON）+ 当前 agent-bindings
    → Spring → core 门面：runTurn(loadedSnapshot, userInput)
         core：AgentFactory.assemble(loadedSnapshot) → AgentInstance
         core：AgentEngine.invoke(instance, …) → 流式/完整结果
         core：返回 TurnOutcome（assistant messages、usage、更新后绑定/配置等）
    → Spring：SessionPersistenceService.save(增量)（事务）
    → Spring：HTTP/SSE 响应
```

**要点**：**Agent 实例不在 Spring 里 new 零散子系统**；**每次对话（或显式缓存策略下的首次）** 在 **已加载会话状态** 之上 **组装** 或 **增量更新** 运行态实例，由 **`core`** 完成；**会话「记住了什么」** 由 **Spring 托管的持久化** 保证。

### Spring 与 `core` 职责对照（速表）

| 维度 | Spring 容器（`api.*` + 持久化 Bean 等） | 领域核心 `core.*` |
|------|----------------------------------------|-------------------|
| 会话记录 / 配置 / 消息 | **读写字段、事务、连接池、迁移** | **定义** 会话与消息 **领域含义**、`Unified*` **形状**；**不** 直接 JDBC |
| 用户发一条消息 | **加载** 全量会话状态 → **调用** core | **组装 Agent**、**执行** Engine、**产出** 待落库增量 |
| 会话级绑定 API | HTTP、DTO、鉴权；**save 绑定结果** | **校验** id、**合并** 策略、**AgentFactory** 再组装语义 |
| Agent 实例 | 可选 **缓存 Bean** 仅作引用或会话外单例，**不** 替代工厂规则 | **唯一** **组装与推理** 真相来源 |
| LLM 厂商格式 | 无（不经手厂商 JSON） | **仅 `LLMClient`** 适配 |
| Request Gate | **唯一实现位置**：`api.gate` Spring Bean；准入前即限流/排队 | **无**；Engine 不感知 HTTP 层队列与背压 |

### 组件职责与边界

#### MCP 与 Agent Engine / Tool 层

- **MCP（Model Context Protocol）** 定位为**工具与资源提供者**：对 LLM 暴露外部工具（tools）、资源（resources）、提示模板等，由 **Agent Engine** 在推理与 Tool/Skill 调度路径上调用；实现上挂在 **Engine / Tool 层**，经 **Capability Registry** 与内置 Tool、Plugin 能力统一登记（便于发现、鉴权与观测）。
- **A2A（Agent-to-Agent）** 只负责 **Agent 之间的消息传递、协作编排与生命周期**（注册发现、路由、主从/对等/任务流/投票等），**不替代 MCP**。多 Agent 协作中若需要调用外部能力，仍由各自 Agent 经 **Engine → Tool/MCP** 完成；A2A 不直接「实现」工具与资源协议。

#### Plugin 与 MCP：两种扩展入口

| 维度 | Plugin（插件） | MCP |
|------|----------------|-----|
| 进程模型 | **进程内**，与 Sophon Server 同 JVM | **进程外**，独立 MCP Server，跨进程通信 |
| 语言与集成 | **Java**，强类型、与框架 API 深度集成 | **跨语言**，标准协议，弱耦合 |
| 性能与部署 | 低开销、适合高频、热路径 | 适合隔离、独立升级、异构栈 |
| 典型用途 | 内置业务工具、紧耦合 Skill、高性能扩展 | 复用社区/第三方工具服务、多语言工具 |

**准则**：二者都扩展「可调用的能力与资源」，但分工不同——**Plugin = 进程内 Java 扩展（强集成、高性能）**；**MCP = 跨进程/跨语言、标准协议**。功能上避免长期重叠却无文档约定：新增能力时优先明确走 Plugin 还是 MCP，并可在统一能力注册表中登记为同一类「Capability」，仅绑定实现方式不同。

### 会话与多 Agent 模型

- **会话（`session_id`）** 以**用户与单次对话上下文**为粒度：**磁盘/库中的会话记录与配置** 由 **Spring 托管的持久化服务** 维护；**加载到内存后的** 消息管线、压缩裁剪、与本轮推理相关的 **运行时状态** 由 **`core` 的 SessionManager / ContextManager** 等配合 **已加载快照** 管理。面向「人与 Agent 的对话」。
- **会话与客户端连接（独占）**：同一 `session_id` 在任意时刻仅允许 **一个活跃客户端连接**持有该会话的控制权（避免双写上下文、流式交错与 tool 调用竞态）。新连接策略由配置约定，例如：**拒绝**、**抢占并断开旧连接**，或要求先显式 **release**；只读查询类接口是否豁免由产品定义。
- **A2A 协作会话（`a2a_session_id`）** 以**多 Agent 编排**为粒度：描述哪些 Agent 参与、协作模式、任务状态与步骤；面向「Agent 与 Agent 的协作」。
- **关系**：`session_id` 与 `a2a_session_id` **彼此独立**，不可混用。用户侧一次对话可**触发或关联**一次多 Agent 协作（对应一个 `a2a_session_id`）；是否允许多个用户会话引用同一 A2A 会话、以及上下文如何传递，由**实现与产品策略**约定。
- **上下文隔离（策略）**：
  - **用户会话上下文**：按 `session_id` 隔离消息与状态，互不泄漏。
  - **A2A 协作状态**：按 `a2a_session_id` 隔离编排状态、步骤输出与 Agent 间传递的中间结果。
  - **交叉引用**：从用户会话进入 A2A 时，仅传递**显式允许**的摘要或任务参数，避免默认把完整用户历史广播给所有参与 Agent。

### 会话级 Agent 绑定配置

- **语义**：每个 **`session_id`** 对应一个**运行态 Agent 视图**（绑定集合）：包含当前启用的 **Tool 集合**、**知识库 / RAG 索引范围**（以及后续扩展的同类项，如 Skill 子集等）。可在会话生命周期内**动态增删**绑定，无需重启进程。
- **配置入口（Spring）**：通过 REST（或 gRPC 门面）提供例如 `PATCH /sessions/{id}/agent-bindings`、或细分为 `.../tools`、`.../knowledge` 等资源；负责 **OpenAPI 契约、鉴权、参数校验、错误码映射**。
- **领域行为（core）**：根据请求计算**新的绑定快照**（与全局 Registry 中已有能力 id、知识库 id 做存在性与策略校验），调用 **`AgentFactory` 再组装**或**对会话内 Agent 实例做受控增量更新**（实现二选一，但对外语义一致）；在**独占连接**下与 **`core` 内运行时状态**一致提交。
- **持久化（Spring）**：绑定变更经 core 校验并返回 **待保存快照** 后，由 **`SessionPersistenceService`（或同职责 Bean）** 写入数据库，保证 **API 成功与落库** 在同一事务策略下一致（与「用户对话路径」相同持久化边界）。
- **与默认配置关系**：会话可继承 Agent 模板 / YAML **默认绑定**，会话级变更为 **增量覆盖**（显式记录 allow-list / deny-list 或全量替换策略由实现定义，并写入文档与 API）。

### 编排层（Orchestrator）

- **定位**：位于 **Agent Engine 之上（或作为独立子模块与 Engine 协作）**，专门承担**复杂工作流**，与「单轮/多轮对话推理」分离。
- **职责**：任务分解、**DAG** 执行、**人机确认（Human-in-the-loop）** 节点、与 A2A 协作编排的衔接（复杂多 Agent 流程可由 Orchestrator 驱动步骤，具体消息仍走 A2A）。
- **目的**：避免 **Agent Engine** 同时承担对话路由与长流程编排导致模块膨胀；简单对话可不经 Orchestrator，直接进入 Engine。

### 能力注册表（Capability Registry）

- **统一抽象**：内置 **Tool**、**Skill**、**MCP 暴露的 tool**、**Plugin** 注册的能力，在内部映射为同一套 **Capability**（元数据：id、描述、参数 schema、来源类型、权限需求等）。
- **消费者**：**HTTP/gRPC API**、**CLI**、**A2A**、**Orchestrator** 均通过同一套**发现（list/describe）与调用（invoke）语义**访问能力，避免各入口各写一套适配逻辑。
- **实现要点**：Plugin/MCP 在加载或连接完成时向 Registry **登记**；卸载或断开时**注销**；与「组件职责与边界」中的 MCP/Plugin 分工一致，仅多一层统一门面。

### Agent 实例与能力组装

- **目标**：Tool（**含经 MCP 暴露的工具**）、**Skill**、**RAG**、**A2A 参与方式**、**Prompt**、**多模态** 等，在实现上**先抽象为可替换的能力单元**（统一元数据、统一调用边界，对外均经 **Capability Registry** 或同构的 `AgentCapability` 接口），再**组装**成面向一次运行或一次配置的 **Agent 实例**（或 `AgentRuntime`），由 **Agent Engine** 驱动推理与调度，而不是在 Controller 或 Spring Bean 中散落拼接。
- **组装职责**：由 **`AgentFactory` / `AgentAssembler`（命名可二选一）** 根据配置（YAML/注册表）解析：启用哪些 capability id、沙箱策略、RAG 索引范围、是否挂载 A2A 角色等，构造**不可变或受控可变**的 Agent 实例；**MCP** 侧能力通过 **MCP → Tool/Capability 适配器** 注入同一抽象，与内置 Tool、Plugin 提供的能力并列。**会话级绑定**（见上节）在工厂入参中体现为**覆盖层**：默认模板 + `session_id` 维度的 Tool/知识库增删结果。
- **调用路径**：`接口层 →（Spring）加载会话快照 → Request Gate → core：AgentFactory.assemble → AgentEngine.invoke(已组装的 Agent 实例或上下文) →（Spring）持久化增量`；Engine 内部只与**统一能力接口**交互，不区分能力来自 MCP 还是进程内 Plugin。
- **与对话统一模型**：**整条 Agent 链路**（见下节「LLM 客户端抽象」）在 **推理与上下文侧**只传递 **`Unified*`** 消息与部件；**不得**在 Engine、Orchestrator、RAG 拼装、Tool 结果写回会话等路径上并行维护一套「厂商形状」的消息树。
- **与 A2A**：单 Agent 实例可声明「协作角色」与对外 A2A 端点；多 Agent 编排仍由 **A2A 子系统 + Orchestrator** 完成，但**每个参与方**本身仍是组装后的 Agent 实例。

### Agent 实例缓存与再组装策略

**目标**：避免 **每轮对话** 无差别 **全量 `AgentFactory.assemble`** 带来的开销；同时在 **会话绑定 / 模型 / 模板变更** 后 **必定** 使缓存失效，保证行为正确。

- **默认策略（推荐首版）**：按 **`session_id`**（及可选 **连接/lease 世代**）在 **`core` 内或经 Spring 注入的进程内缓存**（如 **Caffeine**）中持有 **`AgentInstance` 或其不可变句柄**；**缓存键** 至少包含：`session_id`、**绑定快照哈希**（tool_ids、knowledge_collection_ids 等排序后摘要）、**`SessionConfig` 中与组装相关的子集**（如 `llm.provider`/`model`、agent 模板 id）。**任一会话级绑定 API 或会话配置变更** 成功后，**同步 invalidate** 该 `session_id` 的条目（或由 **版本号单调递增** 使旧键自然失效）。
- **冷路径**：缓存未命中、显式失效、或首连时：**`AgentFactory.assemble(loadedSnapshot)`** 构建新实例并 **put**；**不得**在 Spring Controller 内拼装，仍经 **`core` 门面**。
- **与 Spring 的边界**：缓存 **实现** 可为 **Spring 单例 Bean**（包装 Caffeine），但 **缓存什么、何时失效** 的规则应由 **`core` 门面或 `SessionAgentBindingService`** 与配置变更路径 **统一回调**，避免仅 Spring 知、core 不知导致 **staleness**。
- **多进程 / 未来水平扩展**：进程内缓存 **不跨副本**；若日后多实例部署，需改为 **分布式失效**（如基于 `session_id` 的 topic）或 **放弃实例缓存、仅缓存 Registry 元数据**——首版单进程可忽略。
- **与「独占连接」**：同一 `session_id` 仅一活跃连接时，缓存竞争弱；若策略改为多读者，需定义 **实例是否可共享只读**（通常仍按会话独占，单写入者更新缓存即可）。

### LLM 客户端抽象与统一消息模型（多模型 / 会话内换模 / 多模态 / 流式）

- **问题背景**：同一会话可在生命周期内 **切换 `provider` / `model`**；不同厂商的 **HTTP 入参、消息 role/part 结构、工具调用字段、流式 chunk 形态** 往往不一致；**多模态**（文本 + 图片/音频/文档引用等）在各 API 中的嵌套方式也不同。若把这些差异泄漏到 **HTTP/gRPC 对外契约** 或散落在 Engine/Controller，会导致客户端与编排逻辑与具体供应商强耦合。
- **全链路统一、单点适配**：
  - **Agent 与持久化一律使用统一模型**：从 **会话上下文、历史消息、RAG 注入片段、Tool/Skill 执行结果合并进对话、Engine 多轮状态、Orchestrator 节点输入输出（与 LLM 相关的部分）** 到 **写入数据库**，均使用 **同一套 `Unified*`**（或与其 **1:1 对应的规范 JSON**，由统一模型序列化得到）。**禁止**在除 **`core.llm.providers.*` 内各 `LLMClient` 实现** 以外的代码路径上，把会话消息持久化为厂商原生结构或依赖厂商 DTO。
  - **唯一对外适配边界**：**仅在实际调用远端/本地 LLM 时**，由当前选中的 **`LLMClient` 实现** 将 **统一模型 → 该厂商请求体**；将 **厂商响应/流式 chunk → 统一模型（含 `UnifiedStreamEvent`）**。RAG、Tool、Session、API DTO 层 **不**承担「某家 LLM 的 JSON 拼装」。
- **原则**：
  - **领域统一模型**：在 **`core.llm.unified`**（或与 `AgentEngine` 邻接、可被 `session`/`engine` 依赖的模块）内定义 **与厂商无关** 的 **`Unified*`** 类型（示意命名：`UnifiedChatRequest`、`UnifiedMessage`、`UnifiedContentPart`、`UnifiedToolCall`、`UnifiedStreamEvent` 等），作为 **全 Agent 核心** 与 **LLM 子系统** 之间的**唯一**对话表示。
  - **会话内换模**：`Session` / `SessionConfig` 记录当前生效的 `provider` + `model`；每次调用由 **LLM 门面** 按当前配置 **解析出对应 Client**，将**同一条会话历史（统一模型）** 交给该 Client；若新模型 **不支持** 某类 `ContentPart`（如某模型仅文本），由 **适配层或策略** 在 core 内降级/拒绝并返回明确错误，**不**把「该用哪种厂商字段」推给 API 调用方。
  - **对外契约稳定**：**REST/gRPC 的聊天与补全类接口** 只接受/返回 **Sophon 定义的** 请求体与事件流（见 [HTTP接口参考.md](HTTP接口参考.md)）；**禁止**在公开 API 中透传或并列暴露「原始 OpenAI/DashScope 请求体」作为常规路径（调试专用、受控、可选通道若存在须单独约定且默认关闭）。
- **响应与流式**：
  - **非流式**：HTTP 响应体为 **统一结构**，可包含 **`parts[]`**（文本块、内联图片 URL/base64 引用、结构化说明等），便于多模态与后续扩展。
  - **流式（SSE 等）**：每条事件为 **统一 `UnifiedStreamEvent` 的 JSON 序列化**，区分 **`delta_text`**、**`delta_part`**（多模态分段）、**`tool_call_delta`**、**`usage`**、**`done`**、**`error`** 等类型；**分段语义**与厂商 chunk 一一在适配器内消化，客户端只解析统一事件，不解析厂商原始 SSE payload。
- **持久化（强制约定）**：数据库中的 **消息正文、助手输出、多模态部件、工具调用快照** 等，**以统一模型的规范 JSON 落库**（可含 **`schema_version`** 字段便于迁移）。**物理读写与事务** 由 **Spring 托管的持久化服务** 执行；**反序列化后的快照** 交给 **`core` Engine**。**不在库中**另存一份「仅某厂商可读的 payload」。若某历史消息对新模型不可用，在 **构建请求前** 由 core 做迁移/裁剪策略（与产品约定）。
- **可扩展性（抽象准则）**：
  - **判别联合（tagged union）**：`UnifiedContentPart`、`UnifiedStreamEvent` 等以 **`type` 枚举 + 载荷对象** 扩展新种类（如未来 `video`、`file_ref`、`thinking`），避免为每种新能力复制整条并行类层次。
  - **单一真相来源**：领域只认一套 `UnifiedMessage` 树；新增模态或事件时，**先**扩展统一模型与 OpenAPI，**再**在各 Provider 的 `LLMClient` 内补映射；禁止在 Engine 内写 `if (openai) …`。
  - **前向兼容**：持久化 JSON 允许 **`unknown` / `extension` 部件**（原样保留、换模后若无法理解可降级提示），具体策略在实现中定义；迁移脚本负责 **schema_version** 抬升与字段改名，不破坏「仍为统一模型子集」的不变式。
  - **与 `common`/API**：对外 DTO 与 `Unified*` **字段语义对齐**（可薄映射层），避免 API 与 core 各定义一套相似但不兼容的结构。

### 流式响应与持久化策略

**问题**：SSE/WebSocket **长流** 与 **单请求数据库长事务** 不兼容；若在 **`done` 之前** 不落库，存在 **断线/崩溃** 丢 assistant 片段的风险；若每个 **delta** 都写库，则 **QPS 与锁竞争** 过高。

**原则**：**HTTP 流式** 与 **持久化事务** 解耦；**用户消息** 与 **助手最终消息** 的 **可见提交点** 分开约定；**失败** 可恢复或显式标记不完整。

- **用户消息（`user`）**  
  - **推荐**：在 **调用 `core` 开始本轮推理之前**（或 Gate 与会话 lease 通过后），由 **Spring** 将用户 **`UnifiedMessage`**（或等价 JSON）**先行提交** 短事务（**`pending` / `committed` 状态可选**），使断线后仍能知道「用户说过什么」。  
  - **备选**：与 assistant 一起在 **`done` 后** 同事务写入——实现简单，但若进程在流中途崩溃，**仅用户侧可能丢失**（产品需接受）。

- **助手输出（流式）**  
  - **内存聚合**：`core` 在流式过程中 **在内存中拼接** 完整 `UnifiedMessage` / `parts[]`（及 `tool_calls` 等），**不向 DB 逐 token 写入**。  
  - **提交时机（推荐）**：在收到 **`UnifiedStreamEvent` 类型 `done`**（或等价「本轮正常结束」）后，由 **Spring `SessionPersistenceService`** 在 **独立短事务** 中 **追加 assistant 消息**（及 **`usage` 元数据**）；与 **用户消息** 是否同事务由实现选择，**避免** 横跨整段 SSE 的单一事务。  
  - **超长输出**：若单条消息体过大，可 **分块存储**（同 `message_id` 多行）或 **溢出到对象存储**，仍由 **`done` 或分段检查点** 触发，不在热路径逐字 `UPDATE`。

- **工具调用与多轮**  
  - **Tool 调用记录**：可在 **每次 tool 起止** 时 **短事务追加**（便于审计），或 **与 assistant `done` 打包**——前者 **可观测性更好**，后者 **写放大更低**；架构上 **二者皆可**，须在 **OpenAPI/审计** 需求中择一。  
  - **多轮 tool loop**：每一轮 assistant/tool **回合** 可对应 **一条或一组** 库记录；**`message_id` / `tool_call_id`** 与 **Trace** 对齐。

- **异常与中断**  
  - **客户端断开**：Reactor/Servlet **cancel** 时，`core` 应 **协作式中断** LLM/MCP；**是否** 将已生成 **部分 assistant** 落库为 **`status=incomplete`** 由策略决定（建议：**可配置**，默认 **不落部分** 或 **落摘要**）。  
  - **`error` 事件**：可将 **最后一条 assistant（若有）** 与 **错误码** 同事务写入，或 **仅写审计日志**；**用户消息** 仍应保持已提交（若采用先行提交策略）。

- **与 `AgentInstance` 缓存**：流式路径 **不改变** 缓存键；**绑定变更** 若在流式进行中发生，应由 **会话独占 + 版本号** 避免并发修改，或 **拒绝** 并发绑定 API 直至流结束。

- **一致性表述**：对外 **SSE** 仍 **立即** 推送 **`delta_*`**；**DB 为最终一致视角**，以 **`done` 后快照** 为准（或显式 **`incomplete`**），客户端若以 **重连拉历史** 为准，应与 **服务端落库策略** 在文档中写清。

### 可观测性（结构化 Trace）

- 在 **Simple Metrics**（计数、延迟分桶等）之外，预留 **结构化 Trace**：贯穿一次请求或一次工具调用的链路，建议字段包括：`session_id`、`agent_id`（若适用）、`tool_call_id`、`a2a_session_id`（若适用）、各阶段 **latency**、LLM **token** 用量（若可获取）、错误码。
- **用途**：排查 **A2A 多跳**、**MCP 跨进程** 问题，与审计日志互补；可输出为日志字段、本地文件或对接未来 OTLP（拓展）。

### 背压与请求门控（Request Gate）

**定案（二选一中的主路径）**：**Request Gate 仅为 Spring 托管，不进 `core`。**

- **归属**：实现类放在 **`com.sophon.server.api.gate`**（或同模块下的 `gate` 包），注册为 **Spring Bean**；**禁止** 在 **`core.*`** 内实现队列、全局限流器、与 WebFlux `ServerWebExchange` 绑定的准入逻辑。架构图中 **Request Gate** 与 **API Interface** 同属 **面向用户** 一侧。
- **职责**：在调用「加载会话 → `core` 门面」**之前**，完成 **请求队列**、**并发上限**、超时与拒绝策略；限流维度至少支持按 **`session_id`** 或按**用户/连接**（可配置）。流式响应与多 Agent 场景下避免内存堆积（OOM）或把 **LLM/MCP** 打挂。
- **与 `core` 的边界**：**`AgentEngine` / Orchestrator 不** 接收「是否被 Gate 拒绝」以外的 Gate 状态；**准入成功后**，对 core 而言与普通方法调用无异。**core 不依赖** Spring、**不依赖** Gate 类型。
- **可选（进阶，非默认）**：若将来需要在 **领域层** 表达「本轮预算已耗尽」等与 HTTP 无关的策略，可另设 **`core` 内无框架依赖的窄 SPI**（如 `TurnBudgetPolicy`），由 **Spring 侧提供实现并注入** 到 core 门面——这是 **「core 接口 + Spring 侧实现」**，**不是** 把 **Request Gate** 搬进 core；**默认架构不强制** 该 SPI，以免模糊「用户侧 Gate」与「领域策略」的界限。
- **与 Registry**：Gate 管「**进系统多少 HTTP/连接级活**」，Registry 管「**能调哪些能力**」；二者正交。
- **与「面向用户 / Agent 能力」独立**：**面向用户** 的容量与连接策略 **全部** 在 Spring 侧收敛；**Agent 能力** 的语义 **全部** 在 `core` 收敛；二者 **模块依赖单向**：Spring → core（经门面），**core 不反向依赖 Spring**。
