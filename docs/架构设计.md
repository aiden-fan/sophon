### 组件职责与边界

#### MCP 与 Agent Engine / Tool 层

- **MCP（Model Context Protocol）** 定位为**工具与资源提供者**：对 LLM 暴露外部工具（tools）、资源（resources）、提示模板等，由 **Agent Engine** 在推理与 Tool/Skill 调度路径上调用；实现上挂在 **Engine / Tool 层**，经 **Capability Registry** 与内置 Tool、Plugin 能力统一登记（便于发现、鉴权与观测）。
- **A2A（Agent-to-Agent）** 只负责 **Agent 之间的消息传递、协作编排与生命周期**（注册发现、路由、主从/对等/任务流/投票等），**不替代 MCP**。多 Agent 协作中若需要调用外部能力，仍由各自 Agent 经 **Engine → Tool/MCP** 完成；A2A 不直接「实现」工具与资源协议。

#### Plugin 与 MCP：两种扩展入口

| 维度 | Plugin（插件） | MCP |
|------|----------------|-----|
| 进程模型 | **进程内**，与 Sophon Server 同 JVM | **进程外**，独立 MCP Server，跨进程通信 |
| 语言与集成 | **Java**，强类型、与框架 API 深度集成 | **跨语言**，标准协议，弱耦合 |
| 性能与部署 | 低开销、适合高频、热路径 | 适合隔离、独立升级、异构栈 |
| 典型用途 | 内置业务工具、紧耦合 Skill、高性能扩展 | 复用社区/第三方工具服务、多语言工具 |

**准则**：二者都扩展「可调用的能力与资源」，但分工不同——**Plugin = 进程内 Java 扩展（强集成、高性能）**；**MCP = 跨进程/跨语言、标准协议**。功能上避免长期重叠却无文档约定：新增能力时优先明确走 Plugin 还是 MCP，并可在统一能力注册表中登记为同一类「Capability」，仅绑定实现方式不同。

### 会话与多 Agent 模型

- **会话（`session_id`）** 以**用户与单次对话上下文**为粒度：由 Session Manager 管理消息历史、压缩裁剪、会话级配置与存储；面向「人与 Agent 的对话」。
- **A2A 协作会话（`a2a_session_id`）** 以**多 Agent 编排**为粒度：描述哪些 Agent 参与、协作模式、任务状态与步骤；面向「Agent 与 Agent 的协作」。
- **关系**：`session_id` 与 `a2a_session_id` **彼此独立**，不可混用。用户侧一次对话可**触发或关联**一次多 Agent 协作（对应一个 `a2a_session_id`）；是否允许多个用户会话引用同一 A2A 会话、以及上下文如何传递，由**实现与产品策略**约定。
- **上下文隔离（策略）**：
  - **用户会话上下文**：按 `session_id` 隔离消息与状态，互不泄漏。
  - **A2A 协作状态**：按 `a2a_session_id` 隔离编排状态、步骤输出与 Agent 间传递的中间结果。
  - **交叉引用**：从用户会话进入 A2A 时，仅传递**显式允许**的摘要或任务参数，避免默认把完整用户历史广播给所有参与 Agent。

### 编排层（Orchestrator）

- **定位**：位于 **Agent Engine 之上（或作为独立子模块与 Engine 协作）**，专门承担**复杂工作流**，与「单轮/多轮对话推理」分离。
- **职责**：任务分解、**DAG** 执行、**人机确认（Human-in-the-loop）** 节点、与 A2A 协作编排的衔接（复杂多 Agent 流程可由 Orchestrator 驱动步骤，具体消息仍走 A2A）。
- **目的**：避免 **Agent Engine** 同时承担对话路由与长流程编排导致模块膨胀；简单对话可不经 Orchestrator，直接进入 Engine。

### 能力注册表（Capability Registry）

- **统一抽象**：内置 **Tool**、**Skill**、**MCP 暴露的 tool**、**Plugin** 注册的能力，在内部映射为同一套 **Capability**（元数据：id、描述、参数 schema、来源类型、权限需求等）。
- **消费者**：**HTTP/gRPC API**、**CLI**、**A2A**、**Orchestrator** 均通过同一套**发现（list/describe）与调用（invoke）语义**访问能力，避免各入口各写一套适配逻辑。
- **实现要点**：Plugin/MCP 在加载或连接完成时向 Registry **登记**；卸载或断开时**注销**；与「组件职责与边界」中的 MCP/Plugin 分工一致，仅多一层统一门面。

### 可观测性（结构化 Trace）

- 在 **Simple Metrics**（计数、延迟分桶等）之外，预留 **结构化 Trace**：贯穿一次请求或一次工具调用的链路，建议字段包括：`session_id`、`agent_id`（若适用）、`tool_call_id`、`a2a_session_id`（若适用）、各阶段 **latency**、LLM **token** 用量（若可获取）、错误码。
- **用途**：排查 **A2A 多跳**、**MCP 跨进程** 问题，与审计日志互补；可输出为日志字段、本地文件或对接未来 OTLP（拓展）。

### 背压与请求门控（Request Gate）

- **位置**：位于 **API 层与 Agent Core（含 Orchestrator/Engine）之间**（与架构图中 **Request Gate** 对应）。
- **机制**：**请求队列**、**并发上限**、超时与拒绝策略；限流维度至少支持按 **`session_id`** 或按**用户/连接**（可配置），流式响应与多 Agent 场景下避免内存堆积（OOM）或把 **LLM/MCP** 打挂。
- **与 Registry**：Gate 管「进系统多少活」，Registry 管「能调哪些能力」；二者正交。
