# 核心概念与架构

## 核心概念

### Knowledge（知识库）

- **定位**: 智能体的知识存储和检索能力
- **类型**: 文档知识库、向量数据库、RAG（检索增强生成）
- **特点**: 可持久化、可检索、可管理

### Tool（工具）

- **定位**: 底层功能能力，专注于「怎么做」（How）
- **类型**: 本地自定义工具、MCP 远程调用工具
- **特点**: 细粒度、可复用、专注单一功能

### Skill（技能）

- **定位**: 高层用户交互，专注于「做什么」（What）
- **能力**: 可独立实现，也可组合多个 Tool 和知识库完成复杂任务
- **特点**: 用户友好、可组合、面向业务场景

### 模块间关系

1. **接口解耦**: 各子域通过接口对外暴露能力，默认实现可替换；**不是**「编译期零依赖」，而是**依赖方向清晰、可测试、可插拔**。
2. **依赖方向（默认装配）**: `application`（用例）→ `Skill` / `AgentEngine` → `Tool`、`knowledge`（检索/RAG）、`ai`；`cli` / `web` **仅**调用 `application` 层，不承载核心业务编排。
3. **能力组合**: Skill 与智能体编排可组合 Tool 与知识检索，完成复杂任务。
4. **知识参与方式**: 优先由 **Skill / AgentEngine / application** 编排「先检索再调 Tool」；Tool 若需读库，应依赖 `KnowledgeQueryPort` 等接口，避免直接绑定 `KnowledgeManager` 具体类。
5. **层级协作**: 知识库提供可检索数据，Tool 提供可执行能力，Skill 提供面向场景的组合逻辑。

---

## 架构设计原则

- **模块化**: 各功能模块边界清晰，便于扩展和维护
- **接口优先**: 核心能力通过接口定义，支持多种实现
- **可扩展性**: 预留扩展点，支持新功能和新集成
- **单一编排入口**: 对话、RAG、工具循环的**业务编排**集中在 `core/application` + `AgentEngine` / `knowledge.RAGEngine`，避免 CLI 与 Web 各写一套逻辑

## 分层职责（避免 Manager 重叠）

| 组件                          | 职责                                                                                                                                                                                               |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `SessionManager`            | 会话**生命周期与元数据**（创建、恢复、持久化边界），含 **SessionCapabilityConfig**（Tool/Skill/KB、引用开关、信任级别、Profile 等）的读写与持久化；协调**导出/导入/分叉**；不承载消息裁剪与 LLM 循环                                                               |
| `ConversationManager`       | **消息列表**、角色与顺序；**会话级 system 提示**（与全局 `sophon.ai.system-prompt` 合并策略见 [配置说明](配置说明.md#toc-system-prompt)）；**滑动窗口与/或自动摘要**（见 [产品规格](产品规格.md)）；**编辑后重答**与分支会话的上下文边界                                                                                                                                     |
| `AgentEngine`               | **LLM 调用 + 工具调用状态机**（如 ReAct）；**流式**走 `AIProvider`；通过接口调用 `ToolExecutor`、`AIProvider`；需要 RAG 时调用 `RAGEngine`；**仅暴露本会话已启用且通过风险策略的 Tool**；RAG **仅使用本会话知识库**；**高危 Tool** 走确认或信任级别；**审计**由统一组件记录（见下） |
| `RAGEngine`（位于 `knowledge`） | **RAG 门面**：检索 → 组装上下文 → 调用 `AIProvider` 生成；输出须支持**引用结构**（与 citations 开关一致）；供 `AgentEngine` 或 `application` 调用                                                                                    |
| `core/application/` 包      | **应用用例服务**：聊天（含流式）、Skill 调用、会话能力、用量统计、导出/导入、自检编排等，供 CLI/Web **共用** |
| （建议）`ToolAuditLogger` / 端口  | **Tool/MCP 调用审计**持久化或落盘，参数摘要、会话 id、结果状态                                                                                                                                                          |
| （建议）`UsageTracker` / 端口     | **Token 用量**按会话、按模型聚合                                                                                                                                                                            |

## 领域模型命名（避免混淆）

| 包 / 概念         | 含义                                                                                                 |
| -------------- | -------------------------------------------------------------------------------------------------- |
| `model/`（根下）   | **持久化与运行时领域实体**：`Session`、`Message`、应用级 `Config` 等；**`Session` 与 `SessionCapabilityConfig` 关系见下「Session 与 SessionCapabilityConfig」** |
| `skill/model/` | **SKILL.md（或 skill.yaml）解析产物**：`SkillDefinition`、`SkillMetadata` 等，描述「技能清单与契约」，不等同于 `model` 里的业务实体 |
| `tool/model/`  | **工具契约**：参数 schema、MCP 配置、`ToolResult` 等                                                           |

<a id="toc-session-persistence"></a>

## Session 与 SessionCapabilityConfig（持久化约定）

| 项 | 约定 |
|----|------|
| **关系** | **一对一**：每个 `Session` 对应**至多一份**本会话能力视图；新建会话时创建或继承默认的 `SessionCapabilityConfig`。 |
| **领域模型** | `SessionCapabilityConfig` 可作为 `Session` 的**嵌套值对象**（内存中与 ORM 中一体），或**同表 JSON 列** / **子表一行**持久化；**禁止**在业务代码中散落多份互不同步的副本。 |
| **查询** | 按 `sessionId` 加载会话时**一并**加载能力配置，供 `AgentEngine`、RAG、`SlashCommandRouter` 使用同一来源。 |
| **System 提示（system prompt）** | **与会话绑定**：发往模型的 **system** 角色内容以 **当前会话** 为准；可在全局默认（`application.yml` / 环境变量 / 启动参数）之上做**会话级覆盖**。会话内修改后，仅影响该 `sessionId` 直至再次修改或清除。**持久化目标**：与 `Session` 或 `SessionCapabilityConfig` **一并读写落库**；详见 [配置说明 — system prompt](配置说明.md#toc-system-prompt)。 |
| **迁移** | 若从「仅 Session」演进为「Session + 能力子表」，需提供迁移脚本并在 [ai.md](../ai.md) 或变更记录中说明。 |

## 包分层与命名（建议）

随着类数量增加，**不宜**在 `com.sophon.core` 根下堆放过平级的几十个类。建议实现时**至少**采用二级包名，与职责对齐，例如：

| 包路径（示例） | 用途 |
|----------------|------|
| `com.sophon.core.application` | 用例服务：`ChatApplicationService`、`SessionCapabilityService` 等 |
| `com.sophon.core.session` | `SessionManager`、`ConversationManager` 及与会话强相关的策略 |
| `com.sophon.core.agent` | `AgentEngine`、可选 `AgentToolSource`（与 `ToolRegistry` 合并额外 `ToolDefinition`，供 Skill/知识库工具扩展）；工具循环状态机；**流式与同步共用**同一套 tools 与 `max-rounds` |
| `com.sophon.knowledge`、`com.sophon.tool`、`com.sophon.skill` | 保持与文档一致的顶层域，内部再按 `rag`、`index`、`mcp` 等分子包 |

上述仅为**命名空间组织**，不改变模块依赖方向；**单模块 Maven** 在 alpha 阶段可维持一个 `artifactId`，见 [技术栈 — Maven](技术栈.md#toc-maven-deps)。

<a id="toc-crosscut"></a>

## 横切能力与可观测（包约定）

审计、用量、Tracing 等**横切能力**须在包结构中有固定位置，避免实现类散落在 `application` 各处。建议统一放在 **`com.sophon.core.observability`**（若更强调基础设施边界，也可用 **`com.sophon.infra.observability`**，全项目二选一）：

| 内容 | 建议子包或类名 |
|------|----------------|
| **Tool/MCP 审计** | `…observability.audit`：`ToolAuditLogger` 及持久化适配 |
| **Token 用量** | `…observability.usage`：`UsageTracker` 及聚合存储 |
| **OpenTelemetry**（若启用） | `…observability.tracing`：Tracer 获取、与 Reactor 上下文传播适配 |

**接口**（端口）可定义在 `com.sophon.core.observability.spi` 或 `com.sophon.api`（若后续抽成被依赖模块），**实现**与 SQLite/文件落库同层或紧邻 `storage`。

<a id="toc-public-api"></a>

## 对外 API 与稳定面

| 概念 | 约定 |
|------|------|
| **稳定面** | **`core/application` 暴露的用例 API**（接口或门面类）及其配套的 **DTO / 命令 / 查询对象**（如聊天请求、会话能力补丁、导出结果摘要）。CLI、HTTP、SSE 等适配层**仅依赖**稳定面，通过用例方法驱动业务。 |
| **非稳定面（内部实现）** | 持久化实体 **`Session`、`Message`**、进程内 **`ToolRegistry` / `SkillRegistry`**、**`AgentEngine` 内部状态**等，**不得**作为 REST/开放 SDK 的直接返回类型或路径参数暴露给外部调用方。 |
| **边界转换** | 在 **application 层**（或专门的 `…application.dto` / `…api` 包）完成 **领域对象 ↔ DTO** 映射；`web` / `cli` **禁止**把 `Session` 等实体一路传到控制器再序列化。 |
| **演进与兼容** | 对外形状变更（字段增删、语义变化）需有 **版本策略**（如 URL 前缀 `/v1`、或响应头 `API-Version`）并记入 **CHANGELOG**；破坏性变更需显式说明迁移方式。 |
| **被依赖场景** | 若将来将 `sophon` 作为**库**被其他项目依赖，稳定面宜逐步收拢到 **`com.sophon.api`**（或独立模块），与 `impl` 分离。 |

**一句话**：传输层只认识「用例 + DTO」；领域与注册表留在进程内可演进区域。

## 核心模块（包树）

```
com.sophon
├── core/           # 智能体会话与编排（无 UI）
│   ├── application/         # 应用用例层（CLI/Web 统一入口）
│   ├── observability/       # audit、usage、tracing、spi
│   ├── SessionManager       # （实现可置于 core.session）
│   ├── ConversationManager
│   └── AgentEngine
├── knowledge/      # 知识库与 RAG（RAGEngine、KnowledgeManager、VectorStore…）
├── model/          # Session、Message、SessionCapabilityConfig、Config…
├── storage/        # StorageAdapter、SQLiteStorage…
├── tool/           # ToolRegistry、ToolExecutor、LocalTool、MCP…
├── skill/          # SkillLoader、SkillRegistry、SkillExecutor…
├── ai/             # AIProvider、DashscopeProvider…
├── cli/            # SlashCommandRouter、InteractiveChatCli…
├── web/            # WebFlux 路由与启动
├── config/         # ConfigManager、AppConfig
└── Sophon.java     # 应用程序入口
```

（细分类名与预留类型以本仓库源码为准。）

## 数据所有权与一致性

| 存储                          | 内容                                                                            | 一致性期望                   |
| --------------------------- | ----------------------------------------------------------------------------- | ----------------------- |
| SQLite（等）经 `StorageAdapter` | 会话、消息元数据、**SessionCapabilityConfig**、**Tool 审计**、**用量聚合**、可选**历史消息检索索引**、应用配置 | 与业务事务一致；迁移工具需覆盖         |
| 向量存储 + 文档文件                 | 分块、向量、源文档                                                                     | **最终一致**；索引重建、增量更新需单独策略 |
| 技能目录                        | SKILL.md / 实现代码                                                               | 与进程内注册表同步；热加载范围见 [开发指南](开发与运行.md)      |

**备份与迁移**：迁移关系型存储时，需说明是否**重建向量索引**（通常需要），避免只迁 SQLite 导致检索不可用。
